## Setup

Porcelain (the most used commands) and plumbing (rare to need them) commands.

To see the configs you are using:
```bash
git config --list
```

Usually you configure everything with `--global`, so you don't have to do it every time, unless you want a different setting locally.

```bash
git config --global init.defaultBranch master
```
(`--add` if you already have something else)

## Start

```bash
mkdir foldername
cd foldername

git init # repo initialised
```

A file can be:
- untracked
- staged
- committed

You can check by:
```bash
git status
```

### Staging
```bash
git add filename
# or
git add . # add everything within that directory only (nothing above it)
```

### Commit
A commit is a snapshot of the repository at a given point in time.
```bash
git commit -m "msg"
```

### Log
```bash
git log
```

It shows:
- Who made a commit
- When the commit was made
- What was changed

For better visualisation:
```bash
git --no-pager log -n 10 --oneline --parents --graph
```

### Hashes
What affects a hash:
- The commit message
- The author's name and email
- The date and time
- Parent commit hashes

Git uses SHA-1 (newer versions of Git support SHA-256 as an optional alternative, but SHA-1 is still the default almost everywhere).

#### Plumbing

All the data in a Git repository is stored directly in the hidden `.git` directory. That includes all the commits, branches, tags, and other objects.

Git saves everything as raw compressed bytes (that's why it's small). You'd need a tool like `xxd` to view it directly.

You can also use `git cat-file -p hash` to get roughly the same information in a readable form.

#### Trees and blobs

**Tree**: Git's way of storing a directory
**Blob**: Git's way of storing a file

### Storing data

Git stores an entire *snapshot* of files at every commit (not just the changes).

```text
             Git Objects
                  │
      ┌───────────┼────────────┐
      │           │            │
    Blob        Tree        Commit
                                 │
                              (Tag)
```

- Blob: file contents
- Tree: directory structure
- Commit: snapshot metadata
- Tag: named reference

### Config
```bash
git config --add --global user.name "Ahpatsum"
git config --add --global user.email "ahpatsum@mus.com"
```

These are stored in `~/.gitconfig`, or you can store them locally using `--local`, in which case they go in `.git/config` instead.

To view the local config:
```bash
git config --list --local
# or
cat .git/config
```

It's stored as:
```
[section]
    key = value
```

To view a certain value:
```bash
git config --get <key>
```
where `<key>` is `<section>.<keyname>`.

##### Unset
To remove a key:
```bash
git config --unset section.key
```

##### Duplicates
Git config allows duplicate keys under the same section (similar to a list rather than a single value). To purge all instances of a key from your configuration:
```bash
git config --unset-all section.key
```

##### Remove a section
```bash
git config --remove-section section
```

#### Location
Usually you will only need:
- global: `~/.gitconfig`
- local: `.git/config`

There's also:
- system: `/etc/gitconfig`
- worktree: `.git/config.worktree` — a file that configures Git for part of a project.

The hierarchy:
System → Global → Local → Worktree

## Branching

A Git branch allows you to keep track of different changes separately.
The last commit on a branch is called the **branch tip**.

To check which branch you are on:
```bash
git branch
```

On GitHub, it's usually **main** used as the default branch instead of **master**.

To set a specific default branch name for this repository, you can use:
```bash
git branch -m master main
# or
git config --add --local init.defaultBranch main
```

### New branch
To create and switch to a new branch:
```bash
git branch my_new_branch
# or
git switch -c my_new_branch # create it and switch to it
```

The old command is `git checkout -b`.

To just switch: `git switch branch`

To visualize more you can use `--decorate=full`, but `--oneline --graph` does the same job for most cases.

## Merge

Once you are happy with the changes in your feature, you want to merge them back into the main branch.

#### Merge commits

Merge base: the most common ancestor.

How it works:
- Find the merge base commit
- Replay the changes from `new_branch` onto `main`, starting from the best common ancestor
- Record the result as a new commit
- The new commit has 2 parents in this case

```bash
git merge new_branch # you should be on main
```

After merging, visualize it nicely with `git log --oneline --decorate --graph --parents`.

#### Fast-forward merge

The simplest way to merge:
```text
      C  new_feature
     /
A - B   main
```

The merge base is also the branch tip of main.

`git merge new_feature` — no merge commit is created.

`git branch -d old_feature` — to delete a feature branch once it's merged.

## Rebase

![Git Rebase](/assets/images/git_rebase.png){: width="80%"}

Rebase changes the merge base to the branch tip, without merging them, and leaves the possibility of a fast-forward merge later on.

You can create a `new_feature` branch with HEAD pointing to a specific commit:
```bash
git switch -c feature COMMITHASH
```

The command:
```bash
git rebase main
```

**Merge vs. rebase**: An advantage of merge is that it preserves the true history of the project. It shows when branches were merged and where. One disadvantage is that it can create a lot of merge commits, which can make history harder to read.

A linear history is generally easier to read, understand, and work with.

*Warning*: You should never rebase a public/shared branch onto anything else. Other developers have it checked out, and if you rewrite its history, you'll cause problems for them.

However, on your own branch, you can rebase onto other branches as much as you want.

## Undoing changes

#### git reset --soft
```bash
git reset --soft COMMITHASH
```
Undoes the last commit(s) but keeps the changes in the index (staged) and working tree.

`--soft` is useful if you want to go back to a previous commit but keep all your changes. Committed changes become uncommitted and staged, while already-uncommitted changes stay as they were.

If it's in recent history: `git reset --soft HEAD~1`

#### git reset --hard
Undoes everything:
```bash
git reset --hard COMMITHASH
```

**Danger**: `git reset --hard` undoes the commit and deletes the corresponding file changes for good.

## Remote

In Git, another repo is called a "remote". The convention is to name it `origin` when it's the "authoritative source of truth" (e.g. on GitHub).

```bash
git remote add <name> <uri> # uri can be a local path too
```

## Fetch
```bash
git fetch # bring everything from the remote into the current repo
```

To see the remote's history: `git log origin/main`

### Merge
Just as we merge branches within a single local repo, we can also merge branches between local and remote repos.

```bash
git merge remote/branch
```

You need to `fetch` + `merge` to bring all the remote repo's content into your local copy.

#### GitHub
Git ≠ GitHub. Add a remote:
```bash
git remote add origin https://github.com/username/repo.git
```

To make sure it works: `git ls-remote`

#### Push
```bash
git push origin main # push local main's commits to origin's main
```

Alt options: `git push origin <localbranch>:<remotebranch>`

#### Pull
Fetching is nice, but most of the time we want the actual file changes from a remote repo, not just the metadata:
```bash
git pull [<remote>/<branch>]
```

Set `git config --add --local pull.rebase false` to avoid ambiguity/problems when merging on pull.

#### Pull request
When you add a `new_feature`, commit changes, and push, you can open a pull request on GitHub to propose merging your branch into `main`.

#### Workflow

##### Keep stuff on GitHub
Keep all serious projects on GitHub. That way you always have a backup, and if you're on another computer, you can just clone the repo and get back to work.

##### Rebase vs. merge
You can configure Git to rebase by default on pull, rather than merge, to keep a linear history:
```bash
git config --global pull.rebase true
```

##### Solo workflow
- Make changes to files
- `git add .`
- `git commit -m "msg"`
- `git push origin main`

`git log`, `git reset`, and a few others are useful from time to time, but this is the core loop.

##### Team workflow
- Update your local `main` branch: `git pull origin main`
- Check out a new branch for your changes: `git switch -c new_feature`
- Make changes to files
- `git add .`
- `git commit -m "comment"`
- `git push origin <branchname>` (push to the new branch, not `main`)
- Open a pull request on GitHub to merge your changes into `main`
- Once approved, click "Merge" on GitHub
- Delete your feature branch, and repeat for the next set of changes

#### .gitignore
Files you don't want to commit, like `.env` files or build artifacts.

If you want to ignore something locally without adding it to the shared `.gitignore`, edit `.git/info/exclude` instead.

#### Nested .gitignore
Your `.gitignore` file doesn't need to live only at the root of your project. It's common to have multiple `.gitignore` files in different directories — a nested one only applies to the directory it's in and its subdirectories.

#### Patterns
It would be rough if `.gitignore` only accepted exact file paths. Luckily, it supports:
- Wildcards: `*.txt`
- Rooted patterns: `/main.py` — patterns starting with `/` are anchored to the directory containing the `.gitignore` file, not its subdirectories
- Negation: `*.txt` then `!important.txt`

#### Tips
- To change your last commit message: `git commit --amend` (rewrites the hash — this is destructive/history-altering, avoid on shared branches).
- `git reset --soft` is handy any time you want to uncommit without losing changes (e.g., to re-commit differently instead of rebasing).

## Fork

A fork is a copy of a repository. Forking lets you freely experiment with changes without affecting the original project.

Forking is not a Git operation — it's a feature offered by hosting services like GitHub, GitLab, and Bitbucket. It's essentially a copy that stays linked to the original via metadata.

#### Clone
```bash
git clone uri
cd repo
# make changes
```

#### PRs from a fork
1. Fork their repo into your account
2. Clone your fork locally
3. Create a new branch
4. Make changes
5. Commit and push to your fork's remote branch
6. Open a pull request from `your_username/repo:your_feature` into `original_owner/repo:main`

The original owner can then review and merge your changes straight from your fork.

- Fork if you want to contribute.
- Clone if you just want to experiment.

It's worth adding an `upstream` remote to keep up with the latest version of a repo you've forked:
```bash
git remote add upstream https://github.com/ORIGINAL_OWNER/ORIGINAL_REPO.git
```

This helps you avoid conflicts before opening a PR.

### Reflog
"Reference log." Reflog uses a different format to show the history of a branch or HEAD. The difference from `log` is that if you do a reset, it won't show in `log`, but it *will* show in `reflog`.

### Recovery
To recover something lost:
- Use `git reflog` to find the commit hash
- Use `git cat-file -p COMMITHASH` to find the tree, then find the `blob` hash for the file and print it out (same command, walking tree → blob)

A cleaner way to recover a whole branch state:
```bash
git merge <commitish>
```
`<commitish>` is anything that resolves to a commit (branch, tag, commit hash, `HEAD@{1}`, etc.)

```bash
git --no-pager reflog # find the entry you want
git merge HEAD@{1}    # or whatever index is shown
```

### Conflicting changes
A merge conflict happens when two commits change the same line and Git can't automatically decide which change to keep. This typically happens when the two commits aren't in a parent-child relationship.

If you have a conflict and want to bail out: `git merge --abort`

#### Edit the file
Resolving conflicts is a manual process. Git marks the conflicted sections in the file:
```
<<<<<<< HEAD   (your current branch)
=======        (separator)
>>>>>>> main   (the incoming branch)
```

#### Resolution
After manually editing the conflicting file(s), `add` and `commit` the changes. This tells Git you've resolved the conflict and it can continue with the merge.

⚠️ Make sure to remove all conflict markers before committing.

#### Back to main
To go back to before the merge: `git reset --hard HEAD~1`

- To help avoid future merge conflicts: `git config --global rerere.enabled true`
- Once resolved, switch to main (ours) and fast-forward merge in the other branch (theirs), then delete the merged branch.

#### Multi-conflict
If you want to make a change and commit it without changing the commit message: `git commit --amend --no-edit`

#### Checkout conflict
`git diff` — to see the differences between commits.

You can use `git checkout` to choose which version of a file to keep:
```bash
git checkout --ours filepath
git checkout --theirs filepath
git add .
git commit -m "msg"
```

#### No merge commits
When resolving merge conflicts, Git doesn't auto-generate the standard `Merge branch 'main' into new_feature` message — you have to write one manually. That makes sense: Git doesn't know what you did to resolve the conflict, so it nudges you to document it yourself.

## Rebase conflicts

Full disclosure: a lot of rebase's bad reputation comes from conflicts. It's nothing you can't handle with a bit of practice.

Rebasing feels scarier because it rewrites Git history — if you're not careful, you can lose work (though usually recoverable via reflog). But once you understand what's going on, it keeps your history (and your team's) cleaner and easier to follow.

`--ours` always refers to the branch you're rebasing *onto* (e.g. main).
`git branch` will show `(no branch, rebasing ...)` while a rebase is in progress.

"Accept incoming changes" = `git checkout --theirs`
"Accept current change" = `git checkout --ours`

Example — preserving main's version of a file:
```bash
git checkout --ours filepath
git rebase --continue # continue the rebase
git log --oneline --graph --parents
```

If there was a commit you made but chose to discard in favor of main's version, that commit is simply dropped from history.

#### Repeat resolution setup
A common complaint about rebase is having to manually resolve the same conflict repeatedly — especially with long-running feature branches, or multiple branches being rebased onto `main`.

→ `rerere` to the rescue.

`git rerere` stands for "reuse recorded resolution." It lets Git remember how you resolved a conflict hunk, so the next time it sees the same conflict, Git can resolve it automatically.

To enable it: `git config --local rerere.enabled true`

To force-delete a branch: `git branch -D useless_feature`

#### Accidental commit
If you accidentally commit the resolution of a rebase conflict (instead of running `--continue`):
```bash
git reset --soft HEAD~1 # undo the commit
```
Then simply continue the rebase as normal with `git rebase --continue`.

## Squashing

Every dev team has different standards and opinions on how to use Git: a *single commit* per feature, or a *series of small, focused commits*.

To do the first, you'll need to "squash" your commits together — useful for a clean history, and it also makes it easier to revert a change when the problem is spread across several commits/merges. Squashing is done with `git rebase`.

1. Start an interactive rebase: `git rebase -i HEAD~n`, where `n` is the number of commits to squash.
2. Git opens your editor with a list of commits. Change `pick` to `squash` (or `s`) for all but the first commit.
3. Save and close the editor.

The `-i` flag stands for *interactive* — it lets you edit commit history before Git applies the changes. `HEAD~n` references the last `n` commits.

**Why does rebase squash?**
Rebase is all about replaying changes. When you rebase onto a specific commit (`HEAD~n`), you're telling Git to replay all the changes from the current branch on top of that commit — and the interactive flag lets you tell Git to apply several of those replayed changes as a single combined commit.

#### Force push
If the remote has different history from your local branch (e.g. because you rebased), you can use:
```bash
git push origin main --force
```
This overwrites the remote branch with your local one. It's dangerous but useful — it bypasses the usual safeguards and says "make the remote match this branch exactly." (Prefer `--force-with-lease` when working with others, as it fails safely if someone else pushed in the meantime.)

- When you squash commits, you lose the individual commit history (though it's still recoverable via reflog for a while).

#### Squashing PRs
Common workflow to squash all commits on a feature branch for a pull request:
1. Create a new branch off `main`
2. Do your work, committing as you go
3. When ready, squash all commits into one
4. Push your branch to the remote
5. Open a pull request into `main`
6. Merge once approved

## Stash

`git stash` records the current state of your working directory and the index (staging area) — like a clipboard for uncommitted changes. It stores those changes safely and reverts your working directory to match the `HEAD` commit.

```bash
git stash
git stash list      # list your stashes
git stash pop       # apply and remove the most recent stash
```

`git stash` stores changes in a **stack (LIFO)** structure — you always get the most recent stash first.

⚠️ Don't leave things stashed for a long time; it's easy to forget about them.

#### Multiple stashes
You can stash with a message:
```bash
git stash push -m "msg"
```

You usually won't need this — if you're coming back to something much later, it's better to create a new branch and rebase it later on.

- Apply a stash without removing it: `git stash apply`
- Remove a stash without applying: `git stash drop`
- Reference a specific stash: `git stash apply stash@{2}` (the third most recent) or `git stash drop stash@{3}`

## Revert

A revert is effectively an *anti-commit* — it doesn't *remove* the commit (like `reset` does) but instead creates a new commit that does the exact opposite of the one being reverted. It undoes the changes while keeping a full history of both the change and its undoing.

```bash
git log                 # find the commit hash
git revert <commit-hash>
```

### Diff
`git diff` shows differences — between commits, the working tree, etc.

- Difference between the previous commit and current state: `git diff HEAD~1`
- Difference between the working tree and the last commit: `git diff`
- Difference between two commits: `git diff commit_hash_1 commit_hash_2`

#### Revert vs. reset
- `git reset --soft`: undo commits but keep changes staged
- `git reset --hard`: undo commits and discard changes
- `git revert`: create a new commit that undoes a previous one

Use **reset** when you're working on your own branch and undoing something you've already committed locally. Use **revert** when undoing a change already on a shared branch — it doesn't rewrite history, so it won't disrupt collaborators.

## Cherry pick

Use this when you want a specific commit from another branch, without merging or rebasing the whole thing:
```bash
git cherry-pick <commit-hash>
```

You need a clean working tree to do this.

## Bisect

How do you find a bug?
- **Revert** (common in larger teams)
- **Fail-forward**: write a new commit that fixes the bug

How do you find out *when* a bug was introduced? Instead of manually checking every commit, `git bisect` does a binary search to find the commit that introduced it.

`git bisect` isn't just for bugs — it can find the commit that introduced any change, but bugs and performance regressions are the common use case.

How to bisect:
1. Start with `git bisect start`
2. Mark a known-good commit: `git bisect good <commitish>`
3. Mark a known-bad commit: `git bisect bad <commitish>`
4. Git checks out a commit between the two for you to test
5. Run `git bisect good` or `git bisect bad` based on the result
6. Repeat from step 4 until `git bisect` completes
7. Exit with `git bisect reset`

Checking manually each time is tedious — if you have a script that can tell whether the current code is good or bad, automate it:
```bash
git bisect run my_script arguments
```
Don't forget to make the script executable (`chmod +x`).

**`git blame`**: shows who last changed each line of a file — useful for tracking down context on a change.

## Worktree

A worktree is just the directory on your filesystem where the code tracked by Git lives. Usually it's the root of your repo (where `.git` lives). It contains:
- Tracked files
- Untracked files
- Modified files

`git worktree list` — lists all worktrees you've created.

#### Linked worktrees
Worktrees let you work on different changes without losing work. Particularly useful when:
1. You want to switch back and forth between two change sets without a bunch of `git` commands (rather than branching or stashing)
2. You want a lightweight checkout that's still connected to the main repo

**The main worktree**:
- Contains the `.git` directory with the entire state of the repo
- Heavy — getting a new main worktree requires `git clone` or `git init`

**A linked worktree**:
- Contains a `.git` *file* pointing to the main worktree
- Light — about as cheap as a branch
- Can get complicated with `.env` files and secrets (since they aren't tracked/shared automatically)

**Create a linked worktree**:
```bash
git worktree add <path> [<branch>]
```
`<branch>` is optional — Git uses the last part of the path as the branch name if omitted.

**No duplicate branches**: linked worktrees behave like a normal Git repo — you can create branches, switch, delete, tag, etc. But you **cannot** check out a branch that's already checked out in another worktree (main or linked).

#### Upstream
To see if a branch is checked out in another worktree, look for a `+` next to it in `git branch --list`.

#### Delete worktrees
Worktrees are best for long-lived changes, but eventually you'll need to clean them up:
```bash
git worktree remove WORKTREE_NAME
```

Alternatively, delete the directory manually, then prune:
```bash
git worktree prune
```

## Tags

A tag is a name linked to a commit that doesn't move, unlike a branch. Tags can be created and deleted, but not modified.

List all tags: `git tag`

Create a tag on the current commit:
```bash
git tag -a "tag_name" -m "tag message"
```

Tags are usually used to mark public version releases.

### SemVer
"Semantic Versioning" — a naming convention for versioning software:

`v3(major: breaking changes).12(minor: safe new features).5(patch: safe bug fixes)`

Two purposes:
1. A standard convention for versioning software
2. A signal for how risky/impactful upgrading to a given version will be

Push your tags to your remote GitHub repo:
```bash
git push origin --tags
```
